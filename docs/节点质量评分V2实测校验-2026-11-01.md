## 2. V2 评分口径

达到至少 8 次样本才发布数值评分。评分公式：

`70 × Wilson95下界 + 15 × exp(-节点成功请求中位延迟/5000) + 10 × exp(-延迟MAD/3000) + 5 × 双目标覆盖率`

其中：

- 可靠性 70 分：成功/失败请求按 Bernoulli 结果计算双侧 95% Wilson 置信下界（z=1.96）。
- 延迟 15 分：成功请求延迟的节点级中位数，避免极值主导。
- 稳定性 10 分：成功延迟的中位绝对偏差（MAD），对单个异常慢值更稳健。
- 双目标覆盖 5 分：成功目标数除以配置目标总数；不能只按本轮实际观测到的目标数计算。
- 少于 8 次样本时，`qualityScore` 和 `qualityBreakdown` 为 `null`，状态为 `insufficient_data`。

Wilson 下界把每次请求视作一次 Bernoulli 观测，但同一节点对同一目标的连续请求可能相关。因此它在本项目中是保守的工程证据分，不应解释为严格统计独立条件下的 SLA 置信保证，更不是未来可用概率。

## 5. 目前能得出的结论与不能得出的结论

可以得出：

1. 新评分按预期惩罚失败率、较高延迟和较大延迟离散程度。
2. 同一批样本中，stable、working、unreliable 三组的实际成功率有明显区分。
3. 本机本轮可稳定复测的候选节点数量有限；HTTP 与 SS 在本机本轮表现最好。

不能得出：

1. 不能将本次分数解释为未来一天或一周的可用概率。
2. 不能把 503/504 全部当成节点自身故障；目标站、运营商出口、云端/本地路由及限流均可能影响响应。
3. 不能把本机检测结果外推为 GitHub Actions 云端出口或其他地区用户的表现。
4. 不能仅凭一次连续运行证明 Wilson 观测独立；重复请求存在时间和目标相关性。

## 6. 下一步校准建议

V2 先作为同一检测环境/同一轮次的节点排序分使用，不设置“80 分即长期稳定”之类未经验证的硬标签。要让分数具有长期可解释性，建议累积至少 7–14 天、跨不同时间段的云端与本机快照，并保存每轮的原始样本与出口信息。之后按时间切分训练/验证数据，检查分数区间对应的未来成功率、Brier score、可靠性曲线以及稳定节点的留存率；同一轮/同一目标的请求应按轮次或日期聚类，避免把相关请求伪装成独立样本。完成这一步之前，V2 是透明、可复算的工程评分模型，不是统计校准后的概率模型。

### 6.1 快照留存准备

已在 `.github/workflows/deploy.yml` 的云端探测步骤后增加 `actions/upload-artifact@v4`：每次运行以 `github.run_id` 命名独立快照，保存 `artifacts/health/cloud/report.json`，保留 14 天；该机制不把逐次快照追加到 Git 历史，避免仓库持续膨胀。此设置须在 workflow 修改推送到远端并触发 GitHub Actions 后才开始生效；本次本地验证没有触发云端工作流。

当前报告能区分 `cloud` / `local` 模式并记录目标、轮数、并发、时间戳及逐节点样本，但没有记录可验证的具体出口 IP/ASN。后续分析必须把 cloud 与 local 分层，不能将其混为同一分布；若要比较不同出口，需要另行增加经隐私评估的出口标签。
